# 实施蓝图与计划输出规范与模板

本文档规范 `idea-to-system-blueprint` 产出的核心交付物结构与质量标准。  
**技术栈无关、业务领域无关**：本规范适用于 Web 系统、企业级平台、高并发后台、AI Native 应用、工具平台等各类软件工程。

## 一、《系统蓝图.md》核心章节骨架

蓝图必须是**落地实施级**文档，拒绝空泛概念，做到“研发人员拿到即可开工”。

### 目录结构
1. **第一部分：项目定位与生态位**
   - **1.1 一句话定位**：动宾短语，明确系统解决的核心业务痛点。
   - **1.2 架构分期哲学（自适应分期演进：1期/2期/3期+）**：
     - 单期模式：明确首期即可全量闭环交付的边界，不凑冗余二期；
     - 双期模式：一期（核心业务底座，拿掉高阶噱头依然自闭环）、二期（能力跃升层，叠加高阶能力与护城河）；
     - 多期模式：Phase 1 单体主干闭环 → Phase 2 分布式/多租户扩展 → Phase 3 智能化自治与生态开放；
     - 每一期均必须坚决划定剪裁红线（明确不做清单）。
   - **1.3 竞品分析与生态位矩阵**：
     - 与同类商业产品、开源脚手架、传统简化方案的多维度对照；
     - 本项目的差异化空间与立项防御点。
   - **1.4 核心出彩支柱**：提炼 3~4 个技术或架构维度的核心竞争力。

2. **第二部分：总体架构与模块设计**
   - **2.1 代码工程结构**：展示模块/目录分层树状图与职责划分。
   - **2.2 分层架构拓扑图（Mermaid）**：接入层、业务领域层、扩展契约层、基础设施层。
   - **2.3 模块依赖规则与隔离边界**：
     - 严格规定模块依赖方向（核心层严禁反向依赖可插拔业务模块，通过 SPI / 接口解耦）；
     - 端口与适配器设计（接口在核心，实现在外层）。

3. **第三部分：核心领域与功能设计**
   - 各业务子域的职责与数据流转划分；
   - 核心实体的生命周期状态机图（State Machine）；
   - 关键业务流转与规则矩阵。

4. **第四部分：工程化与作品化落地规格（代码级事实源）**
   - **4.1 数据模型全量设计**：
     - 核心实体表结构清单（主键、业务唯一键、状态、外键关联、时间戳、审计字段）；
     - 关键索引设计（唯一索引防并发冲突、联合索引优化高频检索）；
     - 字段防踩坑说明（如幂等锚、版本号、冗余列的设计依据）。
   - **4.2 API 契约清单**：Method、Path、描述、核心请求/响应模型、鉴权要求。
   - **4.3 核心端到端链路时序图（Mermaid Sequence）**：贯通调用方、服务端、数据库与中间件的典型链路。
   - **4.4 源码深挖与技术亮点地图**：
     - 结合本系统具体业务，挖掘 3~5 个具备技术含金量的深度点（如：高并发防超卖/防重、读写分离与一致性保障、动态 SQL 权限改写、复杂补偿事务、链路追踪与全链路可观测性等）；
     - 明确深挖点的“现象、机制、设计权衡、防踩坑”。
   - **4.5 面试与答辩话术准备**：核心一句话、最难的技术问题攻坚、质量保障策略。

## 二、《实施计划.md》核心章节骨架

实施计划是项目的**执行看板**，把宏大蓝图转化为开发者可每天推进的工单。

### 目录结构
1. **1. 范围与剪裁红线**
   - **1.1 一期做什么**：清晰界定一期交付的最小完整闭环；
   - **1.2 一期明确不做清单**：明确剪裁的外围需求及理由（严防范围渗透与项目延期）。
2. **2. 全局工程约定**
   - 分支节奏、自动化测试门槛（单测/集成测试/真实依赖容器）、数据库迁移管理机制、任务卡最低完成标准（DoD 基线）。
3. **3. 里程碑时间线与 DAG 依赖图**
   - 规划 M0 到 M4 渐进式里程碑：
     - M0：骨架与基础设施（项目脚手架、认证、全局错误处理、日志 Trace、契约生成）；
     - M1：公共底座与基础支撑（用户/权限模型、核心中间件通道、公共服务）；
     - M2：核心引擎与关键业务主链路（核心业务状态机、主流程闭环、事务与一致性）；
     - M3：标准业务扩展与场景应用（利用扩展点快速接入各具体业务模块）；
     - M4：端到端验收走查与作品化收官（全量冒烟、走查清单、亮点台账提炼）。
4. **4. 任务卡清单（Task Cards）**
   - 每张任务卡遵循严格模板（见下文）。
5. **5. 验收走查清单与延期剪裁预案**
   - 端到端走查 Checklist（真实用户视角操作路径）；
   - 延期风险预案与缓冲任务。

## 三、任务卡（Task Card）标准规范

每张任务卡必须遵循以下格式，确保执行时具备强操作性：

```markdown
### T2.01 <任务名称> `预估(人日)`
- **产出**: 
  - 具体交付的代码包、类、接口或 SQL 迁移脚本；
  - 关联的前端页面/组件或路由配置。
- **DoD (Definition of Done)**:
  - 1. 可断言的验收标准（例如：集成测试全绿，覆盖正常分支与并发/边界异常分支）；
  - 2. 页面/接口可向第三人演示的最小闭环操作路径。
- **依赖**: T1.03, T1.05（明确前置卡号）
- **深挖点/设计拍板**: （若涉及核心深度，注明需记录的设计取舍与防坑要点）
```

## 四、质量自检 Checklist（技能执行者检查）

在生成最终蓝图与实施计划前，必须核对以下 5 条：
1. **是否业务自洽**：功能设计与选型是否紧扣该系统本身的业务逻辑，无生搬硬套外来名词？
2. **分期演进是否清晰闭环**：首期是否能独立成立并闭环？各阶段演进路径与剪裁红线是否明确？
3. **模块依赖是否无环**：是否通过接口/SPI明确了核心与业务插件的边界？
4. **任务卡是否有明确的 DoD**：严禁只写“实现某某功能”，必须包含具体的代码产出和可断言标准；
5. **是否包含了深挖亮点与面试话术**：是否有让该项目在面试/答辩中脱颖而出的深度技术点？
